# Step 8 review: compact dependency admission

Status: proposal for review. No implementation is authorized by this document.

## Decision requested

Replace `.lorry/dependencies-v1.toml` with compact generated state at
`.lorry/dependencies-v2.toml`. It commits to a canonical review document and
keeps only execution capabilities that must remain visible in a source diff.

The canonical review document is deterministic but not committed. Lorry
reconstructs it from Cargo.toml, Cargo.lock, verified repository objects, and
compact capabilities. `lorry vendor` displays it before approval; `lorry
review` writes it to stdout for review or CI retention.

This replaces the target-only admission boundary with explicit `(host,
target)` contexts. Host-conditioned build dependencies make target-only
commitments ambiguous: Linux-to-Motor and Motor-to-Motor can select different
host packages. Each supported build context must be reviewed explicitly.

Approval of this document settles the new format and its direct repository
cutover only. Ordinary vendoring reconciliation remains Step 9, removal of the
upgrade transaction remains Step 10, and bootstrap derivation remains Step 11.

## Goals

- Keep Cargo.toml as the only human-edited dependency declaration.
- Keep Cargo.lock as the resolved graph authority.
- Keep verified repository objects as the source-evidence authority.
- Preserve explicit approval of sources and dangerous execution capabilities.
- Fail closed before an uncommitted graph, source, build script, or native-tool
  grant can affect compilation.
- Reduce committed state while retaining a deterministic review report.
- Preserve formatting-independent manifest and lockfile semantics.

## Non-goals

- Step 8 does not add signatures, reviewer identities, timestamps, or keys.
- It does not make Cargo an operational dependency.
- It does not weaken denials, required patches, repository checks, resource
  limits, or native-tool restrictions.
- It does not redesign path or seeded-Git admission.
- It does not edit Cargo.toml or define the final Step 9 update CLI.
- It does not derive `bootstrap/stage2-seed.toml`; that remains Step 11.

## Security model

Compact state is an approval record, not source-integrity evidence. Integrity
comes from Cargo.lock checksums and verified repository objects. The commitment
proves the graph, contexts, evidence, and capabilities match what was reviewed.

The following invariants are required:

1. Lorry never trusts evidence copied from compact state.
2. Repository objects are addressed by the locked checksum and fully verified
   before their evidence enters the review document.
3. Lorry reconstructs the canonical document and verifies its commitment
   before synthesizing any generated allow rule.
4. The actual build host/target pair must be an exact reviewed context.
5. The actual selected registry closure and features must match that context.
6. Every build-script or native-tool grant must be explicit in compact state
   and must match verified source evidence.
7. An explicit configured deny always wins over committed admission.
8. Missing, corrupt, conflicting, or extra evidence fails closed. Build, run,
   and test never acquire a missing object.
9. Unknown keys, unsupported versions, duplicates, noncanonical ordering, and
   malformed hashes are hard errors.

The existing state is unsigned. A committer able to replace it can already
replace its approval facts, so a review commitment does not weaken that threat
model. Resisting an unauthorized committer requires signatures.

## Compact project state

Proposed path: `.lorry/dependencies-v2.toml`.

Illustrative state:

```toml
# Generated by Lorry. Do not edit.
format-version = 2
review-format-version = 1
review-sha256 = "0123456789abcdef0123456789abcdef0123456789abcdef0123456789abcdef"

[[context]]
host = "x86_64-unknown-linux-gnu"
target = "x86_64-unknown-linux-gnu"

[[context]]
host = "x86_64-unknown-linux-gnu"
target = "x86_64-unknown-motor"

[[context]]
host = "x86_64-unknown-motor"
target = "x86_64-unknown-motor"

[[capability]]
package = "libc"
version = "0.2.186"
checksum = "68ab91017fe16c622486840e4c83c9a37afeff978bd239b5293d61ece587de66"
build-script = true
native-tools = []
```

The allowed top-level keys are exactly `format-version`,
`review-format-version`, `review-sha256`, `context`, and `capability`.

Contexts are sorted and unique by `(host, target)`. They record build topology,
not whether a target can execute on its host. Cross and native builds are
separate. A new host or target requires review because host `cfg` expressions
can select build dependencies.

Capabilities are sorted and unique by `(package, version, checksum)`. Each
entry grants at least one capability. `build-script` is required and boolean;
`native-tools` is a sorted, duplicate-free array of supported roles. Native
tools require `build-script = true`. The identity must occur in the reviewed
closure, and a build-script grant requires matching verified evidence.

Packages without build-script or native-tool capabilities do not appear in the
compact file. Exact allow rules for them are reconstructed only after the
review commitment verifies.

## Canonical review document

The canonical document is UTF-8 TOML with LF line endings. It contains no
comments, timestamps, usernames, paths, terminal data, or other host
observations. Lorry is its only writer. SHA-256 covers its exact bytes.

Review format 1 contains these sections:

1. Format facts: review format, source-tree format, Cargo.lock format, and the
   manifest feature-resolver version.
2. The sorted reviewed `(host, target)` contexts.
3. Direct crates.io dependency semantics: alias, package, requirement, kind,
   target selector, optional flag, default-features flag, and requested
   features.
4. Root feature definitions and crates.io patch alias/package semantics that
   can affect registry resolution.
5. Every crates.io Cargo.lock node, including inactive nodes, with exact name,
   version, checksum, and semantic dependency references.
6. For every context, its selected registry packages, host/target compile
   kinds, and activated host/target feature sets.
7. For the union of selected registry packages, the exact checksum, license,
   source-tree digest, and build-script presence from verified repository
   evidence.
8. The build-script and native-tool grants from compact state.

Path packages and required patches remain outside registry admission and keep
their independent rules and source-tree checks. Recording patch semantics that
affect registry resolution does not turn a path source into registry approval.

### Canonicalization rules

- Tables and keys have one fixed renderer-defined order.
- Arrays and repeated tables are sorted by their complete semantic keys and
  reject duplicates.
- Package names and versions use Lorry's parsed canonical values. Checksums and
  SHA-256 digests are exactly 64 lowercase hexadecimal characters.
- Dependency and feature sets are sorted; source ordering in Cargo.toml or
  Cargo.lock is not significant.
- Target selectors use Lorry's canonical parsed representation, not original
  whitespace.
- Cargo.lock dependency references are resolved to exact semantic package
  identities before rendering; original lockfile spelling is not hashed.
- Context resolution is performed independently for each recorded pair before
  any union is formed, so target membership and feature differences remain
  visible.
- Licenses and source-tree digests come from verified repository metadata
  without policy-driven rewriting.
- The renderer has explicit byte, item, package, edge, context, feature, and
  nesting limits. A report that exceeds them is rejected rather than truncated.

Changing any canonicalization or interpretation rule requires a new
`review-format-version`; changing only compact TOML syntax requires a new
`format-version`. A review-format bump invalidates the old commitment and
requires regeneration.

## Validation and policy application

Build, run, and test use this order:

1. Parse Cargo.toml, Cargo.lock, and compact state with strict bounds.
2. Reject an unfinished dependency transaction.
3. Require an exact compact-state context for the discovered host and selected
   target.
4. Resolve all recorded contexts from the locked graph without network access.
5. Look up only selected locked registry objects by checksum and verify their
   repository metadata, archive/source identity, and source-tree manifest.
6. Reconstruct the canonical review document and compare its exact lowercase
   SHA-256 digest with `review-sha256`.
7. Require compact capabilities to match the reconstructed selected packages
   and verified build-script evidence.
8. Synthesize exact generated allow rules from reconstructed evidence and the
   explicit capabilities.
9. Apply system/project policy. Explicit denies, constraints, required
   patches, limits, and native-tool restrictions retain precedence.
10. Continue to unit planning and compilation only after every check passes.

Repository lookup before commitment verification is inspection, not admission.
No inspected source can execute, enter a compiler command, or create a cache
entry until the commitment and policy both pass.

## Review workflow

`lorry review` is offline and non-mutating. With no arguments it reconstructs
the committed document, verifies its hash, and writes exact canonical TOML to
stdout. A human diff may compare a supplied prior report, but imported reports
are untrusted display inputs and never grant admission.

`lorry vendor` constructs the candidate document from staged, verified sources
before publication. Its approval display must include, in stable order:

- direct semantic changes;
- locked node and edge changes;
- context and selected-feature changes;
- added, removed, or changed source evidence; and
- added, removed, or changed capabilities.

After approval, CI retains `lorry review` output as an artifact. It is not
checked in because that would recreate the large synchronized state. Cargo.toml,
Cargo.lock, compact capabilities, and the commitment remain visible in Git.

A hash cannot reproduce an old report after its graph and objects disappear.
Historical comparison requires the CI artifact or two source checkouts; the
compact hash is not a human-readable review record.

## Direct cutover

This is a direct source-tree cutover. Lorry does not read or translate
`.lorry/dependencies-v1.toml`. The cutover patch deletes it and all old fixtures
while adding `.lorry/dependencies-v2.toml` generated from the already reviewed
graph. Lorry then has one state path, parser, writer, and admission meaning.

The cutover must not change Cargo.toml, Cargo.lock, selected packages, source
evidence, or capabilities. Any such difference is a defect in the format
change and stops the patch for review.

## Implementation slices after approval

Keep each patch small and independently tested. Intermediate code may be
inactive, but no committed cutover state supports both formats.

1. In `admission_state.rs`, add the canonical review model, fixed renderer,
   digest, resource limits, and golden tests while leaving active admission
   unchanged.
2. Add the strict compact-state parser and renderer, including exact context
   and capability validation. These types remain internal until cutover.
3. In one direct-cutover patch, replace the old admission model and path in
   `admission_state.rs`; make `engine.rs` reconstruct and verify the commitment
   before generated policy; and make `vendor.rs` produce the candidate report
   and write compact state only after verified repository publication.
4. Update the existing `upgrade.rs` journal filename and recovery tests to
   commit `dependencies-v2.toml` last. Do not otherwise redesign the journal;
   Step 10 removes it.
5. Add offline `lorry review` command parsing and exact report output, then
   cover its byte stability and non-mutating behavior in acceptance tests.
6. In the cutover patch, replace Lorry's and the native fixture's committed
   `.lorry` files, update `spec.md`, `design.md`, and `README.md`, and delete
   every format-1 admission parser, writer, fixture, test, and path reference.

Step 9 then moves candidate reconciliation into ordinary `lorry vendor`; Step
10 removes manifest editing and the old three-file upgrade journal.

## Required tests

- Golden canonical bytes and SHA-256 vectors for an empty registry graph and a
  graph containing inactive nodes, target conditions, features, build scripts,
  and native tools.
- Permutation tests proving manifest/lock formatting and source ordering do not
  change the report.
- Mutation tests proving every semantic graph, context, evidence, or capability
  change changes the commitment.
- Separate Linux-to-Motor and Motor-to-Motor closure vectors.
- Rejection of unreviewed host/target pairs and packages selected only by a new
  host `cfg`.
- Strict unknown-key, duplicate, ordering, bounds, malformed-hash, capability,
  and unsupported-version failures.
- Missing, corrupt, shadowed, and conflicting repository-object failures before
  policy synthesis or compilation.
- Explicit-deny and required-patch precedence after a valid commitment.
- Build-script and native-tool denial when compact capability is absent or
  inconsistent with evidence.
- Missing required compact state, stale commitments, and malformed or
  unsupported compact formats fail before policy synthesis or compilation.
- Vendor creation writes only format 2 and preserves the current state-last
  transaction and interruption-recovery guarantees.
- Source and fixture checks prove no `dependencies-v1.toml` admission path or
  format-1 admission parser remains after cutover.
- Offline `lorry review` byte stability and human diff stability.
- Existing build/run/test, cross-Motor, native-Motor, cache identity, vendoring,
  and second-generation coverage through the mechanically selected Lorry gate.
