QuickJS on Motor OS

The developer image includes QuickJS-NG 0.18.0, a small JavaScript engine, built natively for Motor OS. It runs scripts, has a REPL, and compiles scripts into native programs. The engine is upstream code. Only its platform layer, quickjs-libc.c, and one helper in cutils.h carry Motor OS changes. os.platform reports motor.

QuickJS also runs inside WebAssembly: Javy compiles JavaScript into a WebAssembly module that contains it. This page is about the native engine.

Installed files

Running scripts

qjs hello.js
qjs -e 'console.log(1 + 2)'
qjs

Without arguments, qjs starts the REPL. For more than a few lines of input, use a script file or qjs -e; see the limits below.

Native programs

qjsc -e turns a script into a C program. The normal C compiler builds it with libqjs.a:

qjsc -e -o hello.c hello.js
cc -I/user/lib/quickjs/include hello.c /user/lib/quickjs/lib/libqjs.a -o hello
./hello

Add -m to compile an ES module. qjs can also append bytecode to a copy of itself, with no C compiler involved:

qjs --compile hello.js --out hello
./hello

To embed the engine in your own C program, include quickjs.h and link libqjs.a the same way. The archive holds only QuickJS's objects. The C toolchain supplies mlibc and the rest, as described under C/C++ on Motor OS.

How Motor OS differs

Motor OS has no fork, so processes use mlibc's native spawn.

  • os.exec supports cwd, env, file, usePath, block: false, and stdin, stdout and stderr set to a regular file or to the parent's own stdio. Other descriptors cannot be passed to a child. uid, gid and groups are rejected, because Motor OS has roles instead of Unix IDs.
  • os.waitpid waits for one child or for any child (-1), with WNOHANG. Each child is reaped once, across all Workers. A blocking os.exec throws if another Worker reaps its child first.
  • os.kill supports signal 0, SIGTERM and SIGKILL, with the usual permission checks. SIGTERM always terminates. Other signals to another process return -ENOSYS. There are no process groups.
  • std.popen runs /user/bin/rush -c and returns a normal stream.
  • std.urlGet runs /user/bin/curl. HTTP is tested. HTTPS uses curl's normal certificate checks, but has not been tested end to end.
  • Workers use threads. They wait through the runtime's poll and wake calls instead of pipes.
  • os.exePath() returns an absolute path, also after a chdir.

Not available

  • os.pipe returns null. os.dup and os.dup2 return -ENOSYS.
  • os.symlink and os.readlink fail, because Motor OS has no links (see Filesystem). os.lstat works.
  • Native .so modules cannot be loaded: everything is statically linked.
  • os.ttySetRaw and os.ttyGetWinSize are missing. The REPL assumes 80 columns.
  • os.cputime reports zero, and os.utimes is not implemented.
  • In the REPL, end of input and pasted multiline text are unreliable.

Performance

Large regular expressions over wide Unicode ranges are much slower than on Linux. The cause is mlibc's handling of allocations above 32 KiB. The same issue makes the Test262 run below take about 3.5 minutes on 4 vCPUs, against 35 seconds on a Linux host.

How it is built and tested

There is no QuickJS fork. The Motor OS build fetches the upstream v0.18.0 tag, applies a small patch from the repository, and compiles it with the Motor OS Clang and mlibc. No host QuickJS or CMake is needed.

  • /devtools/tests/quickjs-smoke.sh runs in every developer-image test run. It covers the language and modules, qjsc and standalone builds, processes, Workers, popen, HTTP over loopback, and the C library calls the port relies on.
  • The release developer-image test builds QuickJS's Test262 runner natively in a VM and runs the full upstream configuration. The result, 40/82220 errors, 4802 excluded, 5736 skipped, is the same as on Linux.

Build details, the patch workflow, and the related C library changes are in docs/quickjs.md in the repository.
