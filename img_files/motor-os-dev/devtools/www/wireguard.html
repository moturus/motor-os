WireGuard

Motor OS ships wg-tool for creating and managing WireGuard VPN tunnels, and wg, the daemon that encrypts their traffic. Each daemon provides one IPv4/IPv6 tunnel. Start it explicitly from an Interactive session; the image contains no keys or configurations.

Quick start

wg-tool new
wg-tool add-peer /user/cfg/wireguard/wg0.toml
wg-tool up /user/cfg/wireguard/wg0.toml
wg-tool status
ping -c 3 10.20.0.1
wg-tool down wg0

This sequence assumes you choose wg0, the default config path, and local tunnel CIDR 10.20.0.2/32, with a peer at 10.20.0.1. Review the prompts for your network and exchange public keys with the peer before starting traffic.

Create a configuration and add peers

wg-tool new prompts for the interface name, filename, UDP listen port, local tunnel CIDRs, and physical transport addresses. It suggests the first unused wgN, directory /user/cfg/wireguard, port 51820, and tunnel CIDR 10.20.0.1/24. Choose a distinct local tunnel address for each end. The physical address must already be assigned to a physical interface; the suggestion uses a local UDP bind without sending traffic or consulting DNS.

Enter accepts the bracketed default. Lists are comma-separated; invalid input explains the constraint and prompts again. Creation and peer additions require an explicit yes or y; the default is no and EOF never confirms. After confirmation, new generates keys with the native random source, writes them inside TOML, and prints the public key to exchange. It never overwrites an existing config.

wg-tool add-peer [FILE] prompts for an optional descriptive name, public key, numeric endpoint, allowed IPs, keepalive interval, and optional hidden preshared key. Without a filename, it prompts with /user/cfg/wireguard/wg0.toml as the default. Names become comments; the public key identifies the peer. Existing comments and formatting are preserved.

For example, a Motor OS endpoint using 10.20.0.2 could have:

cidrs = ["10.20.0.2/32"]
listen_port = 51820
name = "wg0"
private_key = "<generated base64 private key>"
public_key = "<derived base64 public key>"
transport_addresses = ["192.0.2.2"]

# Peer: office laptop
[[peers]]
allowed_ips = ["10.20.0.0/24"]
endpoint = "192.0.2.1:51820"
# persistent_keepalive = 25
# preshared_key = "<optional shared base64 32-byte key>"
public_key = "<other peer's base64 public key>"

Replace the example physical addresses and key placeholders with your own values. cidrs assigns local tunnel addresses; allowed_ips supplies remote routes and peer ownership. Configure the other peer with Motor OS's public key, a tunnel address such as 10.20.0.1, and an allowed prefix covering Motor OS's 10.20.0.2/32. Permit the listen port on the outer UDP network.

Endpoints must be numeric addresses, with bracketed IPv6 syntax such as [2001:db8::1]:51820. DNS names and explicit IPv6 scope IDs are unsupported. Omit the endpoint for a responder that learns it from authenticated peer traffic; at least one side needs a reachable endpoint. Keepalive defaults to off; 25 seconds is a common NAT-mapping interval. If using a preshared key, exchange it separately and configure the same value at both ends.

Inner and outer IP families are independent. For inner IPv6, add a local CIDR such as fd20::2/128 and a peer prefix such as fd20::/64. For outer IPv6, select an assigned physical IPv6 transport address. At most one physical transport address per family is accepted. Each allowed-IP family needs a local tunnel address.

name and private_key are required. Names contain 1–31 ASCII letters, digits, underscores or hyphens, independently of the filename. public_key may be omitted in a handwritten file; when present it must match the private key. Keys decode from base64 to exactly 32 bytes. Zero peers is valid, but such an interface cannot exchange tunnel traffic.

Configuration permissions

Keep the TOML private: it contains the private key and any preshared keys. The tool creates files with rwxrw---- and its private directory with rwxrwx---, in System/Interactive/None order. Interactive processes share that access; None has none. Both programs reject None-readable configs and None-writable directory ancestry. See Filesystem.

new and add-peer require CAP_FS_WRITE and filesystem access. new also needs CAP_NET for discovery. Writes use private staging files and preserve permissions. A custom parent directory must already exist; the default private directory can be created after confirmation. Run only one tool instance at a time and avoid concurrent manual edits.

Start, inspect and stop

wg-tool up FILE starts a detached Interactive daemon and waits for local activation. The daemon survives tool, terminal and SSH-session exit. The launcher needs CAP_NET, CAP_SPAWN, and CAP_SPAWN_DETACHED. The shipped /user/cfg/rush.toml includes:

spawn-detached = ["rmux", "wg-tool"]

If your customized Rush config lacks wg-tool, add it and start a new shell. Only the launcher needs spawn authority; the daemon receives CAP_INTERACTIVE | CAP_NET. Both programs require Interactive authority; System callers are rejected. See Capabilities.

wg0: up (pid=..., peers=...) confirms local registration. A successful handshake and peer reachability still need checking. wg-tool status shows loaded settings, public keys, lifecycle state, uptime, snapshot age, peer endpoints, handshake ages and tunnel byte counters. It sends no WireGuard traffic, and works even if the original config has moved or been deleted. Snapshots refresh on the 250 ms tick. A missing session means none (no current session), not necessarily that no handshake ever occurred.

Probe a configured peer explicitly with ping -c 3 10.20.0.1. To answer incoming peer pings, Motor OS needs auto_icmp_echo_reply enabled in /system/cfg/sys-net.toml. For more detail, use:

stats providers
stats get PID
stats list

Replace PID with the daemon PID. Its wg:PID provider exposes authentication, ownership, drop and timer counters; sys-io also exposes net.ip_device.* queue/buffer counters and net.udp.tx_boundary_drops. See Logs and diagnostics.

wg-tool down wg0 waits for device retirement and physical UDP binding release. It removes routes and addresses, fails existing tunnel sockets, and leaves the config and keys on disk. New connections use remaining routes, including the physical default. Stopping an absent interface succeeds; a timeout reports an unconfirmed outcome, which should be inspected with status.

add-peer edits only the saved config. Apply changes with an explicit down/up; repeating up fails instead of reloading. For foreground diagnostics, run wg FILE and stop it with Ctrl+C or wg-tool down NAME. A silent peer leaves routes installed; physical transport-address loss ends the daemon. There is no automatic restart or boot startup.

Routing and limits

New TCP connections, ping and destination-aware UDP binding select matching tunnel routes automatically. Ordinary wildcard UDP binding still selects a physical or loopback address; bind to a tunnel address when needed. Existing sockets do not migrate. WireGuard does not change DNS servers: DNS queries follow the route to the configured server, whose address must be covered to tunnel DNS.

Peer ownership uses longest-prefix matching on outgoing destinations and incoming authenticated sources. Nested prefixes are allowed; duplicate exact prefixes and duplicate peer public keys are rejected. While the device exists, packets with no matching peer are dropped rather than sent as plaintext through the physical default. Removing the device removes its routes; there is no persistent kill switch.

  • MTU: 1420 bytes; at most 16 peers, 16 local addresses and 128 allowed prefixes per daemon; config size at most 64 KiB.
  • sys-io allows four active or retiring packet devices. Names, addresses, identical route prefixes and physical listen ports must not conflict.
  • Inter-interface forwarding, bridging, automatic transport failover, live configuration reload and tunnel PMTU propagation are outside v1.

Troubleshooting

For startup failures, check config permissions, launcher capabilities, assigned physical addresses, UDP port conflicts and device/address/route conflicts. For an active tunnel that cannot reach its peer, check the numeric endpoint, exchanged keys, reciprocal allowed prefixes and authentication/drop counters. The peer must answer ICMP echo requests for ping to succeed.

Startup and control operations have five-second deadlines. If activation is unconfirmed, inspect the reported PID with wg-tool status before starting again. A timed-out stop can still finish. Discovery/query failures are reported as errors, not treated as proof that no interface exists.

Use wg-tool --help or wg-tool COMMAND --help for syntax. Ctrl+C, declined confirmation and EOF exit 130; syntax errors exit 2 and operational errors exit 1. Prompts and errors go to stderr, results to stdout. Errors omit keys and preshared keys; status is human-readable rather than a versioned scripting API.

How it works

wg holds keys, peers, cryptographic state and timers in a separate process using boringtun's WireGuard protocol implementation. It registers an IP device with sys-io and transfers complete inner IP packets over native IPC. sys-io continues to own application sockets and the TCP/IP stack, and carries encrypted outer UDP traffic through the physical network. Applications keep their existing socket APIs.

Application sockets
  ↕ socket IPC
sys-io: inner TCP/IP
  ↕ IP packet IPC
wg: peers and encryption
  ↕ UDP socket IPC
sys-io: physical network

The two sys-io entries are one process. Device lifetime follows the daemon: unregistering or exiting removes its routes and addresses and releases queued work.

Testing and source

From a repository checkout with VM test networking configured, the focused guest gate builds its image and tests against a hermetic local host peer:

src/tests/test-wireguard.sh
src/tests/test-wireguard.sh --release

It covers config creation and edits, permissions and capabilities, discovery, malformed IPC, startup/stop failures, detached lifetime, and IPv4/IPv6 interoperability. The host tests run with cargo test --manifest-path src/bin/wg/Cargo.toml --locked (add --release for release). These checks are included in src/tests/full-test.sh and do not require Internet access.

The repository's WireGuard design and usage document has the full configuration, ownership, bounded I/O and control-protocol details. Implementation lives in src/bin/wg.
